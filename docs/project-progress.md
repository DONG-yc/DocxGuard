## 1. 一句话结论

项目已经打通“检查 → 计划 → 预演 → 执行 → 重建 DOCX → 复检与差异验证 → 构建报告 → 文件发布”的 CLI 闭环。

CLI apply 复用来源绑定计划与完整构建管线，将 output.docx 和 build-report.json 写入同级临时目录，核对磁盘哈希后整体发布到一个不存在的结果目录。已有文件或目录不会被覆盖；普通失败和取消会清理本次临时文件，无法清理的路径会明确报告。

批量计划沿用同一条构建链路。所有修改通过前置条件检查、完整输出复检和结构差异校验后，CLI 才会发布一份 DOCX 和一份构建报告。Agent 接入、真实模板与视觉兼容评测、安装发布仍待完成。

## 4. 当前真正能做什么

目前核心库已经可以：

- 安全检查并读取一个不受信任的 DOCX 包；
- 建立 Part 与 Relationship 图；
- 找到真正的 Word 主文档 Part；
- 建立只读语义索引；
- 精确定位普通文本，即使文本跨越多个 Run；
- 生成带强前置条件的单操作文本补丁计划；
- 在不修改源文件的情况下，对内存中的主文档 XML 副本执行替换或删除；
- 拒绝复杂字段、修订内容等当前不能保证安全修改的结构；
- 在执行后重新解析 Word XML、重建索引并验证结果；
- 从原包和执行产物重建新的完整内存 DOCX，重新通过既有读取管线；
- 独立验证主 XML 的改动范围，并核对其他所有条目的解压后内容；
- 返回输入/输出哈希、逐条目比较结果，以及条目名/XML 路径诊断。
- 通过 DocxBuildPipeline 返回同次构建的 DOCX 和 JSON v1.0 报告；报告包含定位、前置条件摘要、预期/实际输出段落哈希和全部检查状态。
- 在失败时保留分层错误码，禁止返回部分产物；返回的集合和字节副本不能反向修改已发布证据。
- 通过 `multi-plan` 从请求数组生成来源绑定的多补丁计划，并拒绝同一段落中的重叠目标、未解析请求和超限批次。

CLI 已可通过 inspect 检查实际文件、plan 生成可保存的计划、dry-run 完成真实预演、apply 保存经过验证的结果。详见 [inspect](cli-inspect.md)、[plan/dry-run](cli-plan-and-dry-run.md)及 [apply 使用说明](cli-apply.md)。

目前还不能：

- 保证任意 Word/LibreOffice 文档的视觉兼容性或分页完全不变；
- 提供任意输出文件覆盖、断电级事务恢复或自动清理历史残留的功能；
- 编辑表格结构、替换图片或修改页眉页脚。

## 6. 下一阶段的具体安排

### Day 9：安全重建 DOCX（已完成）

目标：把修改后的主文档 XML 写入一个全新的内存 DOCX 包，原文件保持不变。

完成标准：

- 精确替换由 Relationship 选出的主文档条目；
- 其余条目逐项复制，不自行改名或重排语义；
- 禁止原地覆盖输入文件；
- 对输出条目数量和大小继续执行边界限制；
- 新包能被当前读取管线再次完整解析；
- 增加正常路径、损坏包、重复条目和资源上限测试。

### Day 10：完整输出复检与 Structural Diff（已完成）

目标：证明修改只发生在允许发生的位置。

完成标准：

- 从 ZIP 预检开始重新检查输出包；
- 比较输入/输出的 Parts、Relationships、Content Types 和媒体资源；
- 默认只允许主文档 Part 的预期文本节点发生变化；
- 非允许变化导致构建失败，并产生可定位的诊断信息。

### Day 11：Build Report 与不可变产物契约（已完成）

目标：让每次修改都可以解释、审计和回滚。

完成标准：

- 报告输入/输出哈希、目标 Part、定位结果、前置条件和后置条件；
- 记录变更摘要、拒绝原因和验证结果；
- 明确源文件始终不变，失败时不留下半成品；
- 为后续 CLI 输出稳定的机器可读结果。

实现与边界：详见[构建报告契约](build-report.md)及 [ADR 0011](adr/0011-versioned-build-report.md)。原始输入始终保留；Day 14 已补齐新目录发布和失败清理，但不提供被覆盖版本恢复 API，也不承诺断电事务恢复。报告是执行证据，不是用户批准凭据。

### Day 12–Day 14：CLI MVP

- Day 12：`inspect`，查看包、主文档和可定位文本（已完成）；
- Day 13：`plan` / `dry-run`，生成并验证补丁计划（已完成）；
- Day 14：`apply`，发布新 DOCX 与 Build Report，并定义稳定错误码（已完成）。

Day 14 的第一版“可交付 MVP”已实现：用户能从命令行输入 DOCX 和来源绑定计划，获得经过验证的新 DOCX 与报告。结果采用新目录中的两个固定文件，要求父目录已存在；不支持覆盖已有目录。

### Day 15：多补丁计划与冲突检测（已完成，计划层）

- `BoundMultiPatchPlan` 记录请求数组、完整前置条件、来源哈希和确定性操作 ID；
- `multi-plan` CLI 支持请求文件和机器可读失败报告；
- 任意未解析请求、同一段落的重叠区间、空批次、64 项上限或 4 MiB 上限都会拒绝整个批次；
- 生成的计划可交给 Day 16 的 `dry-run` 和 `apply`。

详见 [multi-plan 使用说明](cli-multi-plan.md) 和 [ADR 0015](adr/0015-multi-patch-conflict-plan.md)。

### Day 16：多补丁执行与全成全败构建（已完成）

- `dry-run` 和 `apply` 按计划协议识别批次，重新核验来源和全部前置条件；
- 同一批次使用原始段落坐标重建受影响的 Run，执行后核对段落、Run 和表格结构；
- Structural Diff 核对每个修改后的 Run，并校验其他包条目的内容哈希；
- 批次报告使用 `docxguard.multi-text.v1`，每个操作记录所在段落应用全部补丁后的预期和实际哈希；
- 构建任一环节失败时没有输出产物。通过验证后，`apply` 将 DOCX 和报告发布到同一个新目录。

### Day 17：MCP Server（已完成）

- 通过本地 stdio 暴露检查、生成计划、预演和发布。CLI 与 MCP 共用计划加载和构建发布路径；

- 预演与发布使用同一来源绑定计划。源变化后先重新检查和预演，发布前确认新结果；
- MCP 进程测试验证多段落同词的消歧流程、指定范围后预演通过、来源变化后拒绝旧计划，且预演不落盘。
